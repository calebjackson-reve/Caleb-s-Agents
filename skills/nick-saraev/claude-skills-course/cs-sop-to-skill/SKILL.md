# SOP to Skill: Nick's core build method

**Source:** Nick Saraev, "CLAUDE SKILLS FULL COURSE: Automate Your Work (2026)", chapters 6-8 (https://www.youtube.com/watch?v=sduaTkhIm_w&t=930s)

## What Nick teaches

Nick's rule of thumb: **"If you have a standard operating procedure, you have a skill."** Skills are "the evolution of standard operating procedures just for agents." SOPs and checklists are for humans. Skills are the same thing translated into the native format agents read, which is a markdown (.md) file.

His PB&J example: a new hire gets a checklist (take bread out of basket, put jam on one side, put peanut butter on the other, stick them together). A skill is that same checklist, organized as markdown with headers (`#`), backticks for file names, and links, so the agent can parse it. You never hand-write the markdown. You give the agent bullet points and a brief description and it assembles the optimal skill format for you.

As of recording, the skills spec is "not baked directly into the models," so the one extra thing you must do is give the agent the spec. Nick's setup:

1. **Build a condensed `skillspec.md`.** He went to Anthropic's Claude Code docs "Extend Claude with skills" page, copied the entire thing, fed it to the LLM and said: "I want you to really, really shorten this, compress this, significantly increase the information density, because I don't want this to be 500 lines. I want this to be 150 to 200." The result covers the skill definition, file structure, locations and formatting options. (He gives his away free via a Google Drive link in the video description.)
2. **Make the spec your CLAUDE.md.** CLAUDE.md "is just the prompt that's injected at the top of every new conversation." Any file in the root directory named `CLAUDE.md` (capital C, lowercase md) is automatically prepended. He renamed his existing one to `old CLAUDE.md` and made the spec the new `CLAUDE.md`. If you have other stuff in CLAUDE.md, paste the spec in alongside it, but keep it "in as few lines as humanly possible."
3. **Open a new agent window and describe the task in plain language.** Nick used Wispr Flow voice transcription. His inbox-cleanup request, roughly verbatim:

   > "I'd like to build a Claude Code skill that goes through my inbox, identifies all unread messages, reads all of the unread messages, and then marks as read all of the ones that aren't important to me or high priority. My definition for important is basically anything that isn't automatically generated. If the email is automatically generated by a service or it's a simple notification email, it's not important. If the email is written by some cold email copywriting fellow who's trying to reach out and get my business, it's not important. The only stuff that is important are emails that are personalized, customized, and that give off the vibe that they were written basically just for me."

4. **What the agent does with it:** it first scans existing skills and code in the workspace to reuse anything relevant ("we don't really want to rebuild the wheel"), flips into plan mode for anything slightly complicated, finds existing config (his Gmail config files), writes the `SKILL.md`, writes a helper script (`inbox_cleaner`), then tests end to end "because that's just what's in our spec sheet."
5. **Run it at least once, then amend.** "You have to test and amend." On the first run the agent asks for anything it still needs, or builds the asset itself (an Excel file, for example). You can also hand it assets like contacts or PDFs.
6. **Review before destructive actions.** When the agent asked "do you want me to mark these 97 emails as read?", Nick said: "No, I'd actually like you to show me all of the 97 that you marked as read so that I could take a look and tell you if there are any exceptions." It listed them (79 were from a broken Make scenario, plus cold outreach, sponsorship pitches, renewals). Then he said "Nope, mark all as read."
7. **Run it from a fresh instance with a slash command.** Open a new Claude instance ("we have to go new just because of how skills work"), then `/inbox-cleaner`. Because it runs from the SOP it is "repeatable, consistent, and dependable."
8. **Modify with one line.** "I've got a ton of unreads. Could you actually go through and fetch a thousand instead of a hundred?" The agent added a `-a` (amount) flag to the script and passed 1000.
9. **Self-healing.** If the script breaks, a service is down or there's a rate limit, the agent "will identify the problem and then automatically go through, fix it, and then rewrite its own skill." Nick: skills are "like an ambitious intelligent staff member who sees a checklist, notices there's a gap and then chooses to fill it."

The output SKILL.md Nick got had front matter (`name: inbox-cleaner`, a description with "Use when cleaning inbox, triaging email, or clearing unread notifications", and `allowed-tools` for Read, Grep, Glob, Bash), then a title, goal, "what counts as important", and "what gets marked as read".

## Step by step

1. Confirm a compressed skill spec is loaded in context. In Caleb's repo, check whether `CLAUDE.md` or a `skillspec.md` already covers the SKILL.md format (front matter, folder layout, test-then-patch rule). If not, build one: fetch the Anthropic skills docs, compress to 150-200 lines, place it in CLAUDE.md or reference it from there.
2. Ask Caleb for the SOP in his own words. Accept messy input: voice dictation, a bulleted list, a screenshot of a checklist, or an existing Google Doc. Pull out: the trigger, the inputs, the definition of "done", any judgment rules (like Nick's "what counts as important").
3. Scan the repo for existing skills, scripts and config (CRM credentials, Gmail config, templates) that the new skill can reuse. Say what you found.
4. For anything beyond trivial, write a short plan first: skill name, the steps, which parts become a script, what assets are needed.
5. Create `.claude/skills/<skill-name>/SKILL.md` with front matter (`name`, `description` with "Use when ..." triggers, `allowed-tools` if applicable), goal, rules, numbered steps. Put scripts next to it (Nick uses a folder he calls `execution`).
6. Run it once end to end on real data. Stop and show Caleb the proposed changes before anything is sent, deleted, marked, paid for or published.
7. Capture every mistake from the first run and patch the SKILL.md or script so the next run doesn't repeat it.
8. Tell Caleb to open a fresh Claude instance and run `/<skill-name>`.

## Templates / prompts

Request template (voice or typed):

```
I'd like to build a Claude Code skill that <does X>.
Trigger: I'll say "/<name>" or "<natural phrase>".
Inputs: <where the data lives: CRM export, Gmail, a folder, a Google Sheet>.
Rules: <my definition of important / qualified / ready, in plain words>.
Output: <a list, a sheet, drafted emails, a report>.
Before doing anything irreversible, show me the list and let me approve.
Test it once on real data, then fix whatever broke and update the skill.
```

CLAUDE.md addition (short version of what Nick does):

```markdown
# Skills
- A skill lives at .claude/skills/<name>/SKILL.md with YAML front matter (name, description, optional allowed-tools).
- The description must say what it does and "Use when ..." with trigger phrases.
- Keep SKILL.md short. Put deterministic work in scripts beside it.
- After creating or changing a skill, test it end to end once and patch the skill with what you learned.
- When a skill fails at runtime, fix the cause and update the skill so it does not recur.
- Never send, delete, pay or publish without showing the user the list first.
```

Resulting skill skeleton:

```markdown
---
name: new-listing-launch
description: Runs Caleb's new-listing checklist from signed listing agreement to live marketing. Use when Caleb says "new listing", "launch this listing", or "listing checklist".
```

## Pitfalls Nick calls out

- The spec is not in the model. Without a skill spec in context the agent will produce a sloppy or wrong format.
- Don't bloat CLAUDE.md. Keep the spec section as short as possible since it loads into every conversation.
- Skills load at startup, so a brand-new skill needs a new Claude instance before the slash command works.
- Always review before destructive actions. Nick refused the blanket "mark 97 as read" until he saw the list.
- The first run will find gaps. That's expected, not failure. Amend and rerun.
- Auto-captions aside, Nick points out that skills get noisy fast if you let them do "everything." Build the one task, test it, then extend by a line at a time.

## Verification

- `.claude/skills/<name>/SKILL.md` exists with valid front matter and a "Use when" description.
- A fresh Claude session lists the skill and `/<name>` triggers it.
- The first test run produced the expected output (list, sheet, drafts) and stopped before any irreversible step.
- After the first run, the SKILL.md or script shows at least one patch from what was learned, or a note that nothing needed changing.
